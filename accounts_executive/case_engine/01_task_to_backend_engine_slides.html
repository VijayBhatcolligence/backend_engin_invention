The problem

Today, the backend depends on who designs it

Different answers

Two engineers given the same screen design different tables, names and rules. Every later module inherits the mismatch.

Missed controls

A check shown on screen (e.g. "GSTIN already our vendor") is easy to forget in the backend. Then it exists only in the UI and can be bypassed.

Accounting surprises

Ledger effects get designed late, inside each module. Sub-ledgers stop tying to the control accounts and audit trails differ by team.

Goal

A repeatable recipe: the screens are already agreed, so the backend should follow from them by fixed rules, not by taste.

The idea

Two agreed sources in, complete backend out

The app is never changed and the task doc is never edited. The method reads both and engineers the logic underneath.

Ground rules

Five rules that make the answer repeatable

1
The app is fixed; the task doc is read.We read the agreed screens and the agreed task cards. We never ask for either to change to suit the backend.
2
Same input, same output.Every name, field type and table comes from a written rule, never from personal preference.
3
Never invent.If both sources are silent, use a listed default or record a gap for a decision. Nothing is guessed silently.
4
Everything is traced.Every table, rule and API points back to the screen item or task-doc fact it came from, and every one of them is used.
5
One owner per fact.Each fact has one owning area. It changes only through an action; everyone else only reads it or listens.

Steps 1–9 · the 9 engine words

Nine questions, always in the same order

1 · Context

Who owns each fact?

Party identity → party master. Terms → finance. Ledgers → accounting.

2 · Entity

What record is created?

One request, with the life cycle the screen shows.

3 · Action

What can a person do?

Each button is one action, guarded by the checks on screen.

4 · Event

What happened?

Every action announces one fact, e.g. "request approved".

5 · Reaction

What does the system do next?

Automatic work, done by a named automation, never anonymous.

6 · Approval & timer

Who signs off, by when?

One approval per checker block; deadlines and reminders.

7 · Query

What does each list show?

Every list and tile answers one business question.

8 · Authority

Who may do what?

Checked by the server on every call. The screen only hides buttons.

9 · History

What is kept for ever?

Each action writes its record, receipt and change log in one go.

Controls built in

What an auditor gets by default

Maker–checker

The person who prepares a request can never approve it. Each checker approves only the block they own. Every "never" in the task doc becomes a refusal, with a test.

Checks on the server

Every check on screen is also enforced by the backend. A request that breaks a rule is refused, with the rule's id.

Limits have owners

Every number (45 credit days, 48 h deadline, 80 % name match) is a setting owned by a named role, e.g. the Accounts Manager.

Nothing is erased

Records are never deleted or rewritten. A correction is a new action or a new version, so history is complete.

Full receipt

Every action records who did it, in what role, what changed and what came of it, all in one step.

Sensitive data

PAN, bank account, phone and email are encrypted and masked. Every full view is logged.

Accounting · team lead's design

Every task is one of three kinds

Master

Vendor, customer, item, bank

Records the master. No journal entry. May open a sub-ledger account under the right control account.

Operational

Purchase request, PO, sales order

Records the document. No journal entry. An open PO feeds commitments.

Financial

GRN, invoices, receipts, payments, payroll

Records the document and raises one accounting event that the posting engine turns into journal lines.

When things go wrong

Failures are planned, visible and never undone by deleting

If…Then…
An action fails halfwayNothing is saved. The user can safely press the button again; it never happens twice.
An automatic step failsRetried 5 times over about 7 hours. Then it lands in the owning team's exception queue with a notice.
The chain stops midwayFinished steps stay done. A retry continues from the failed step; nothing is reversed.
The GST portal or bank is downThe user sees "service unavailable" and tries later. The request is unchanged.
A wrong value went liveCorrected by a new, approved action. The old value stays in history.
A request sits stuckAfter 2 hours the owner is alerted.
